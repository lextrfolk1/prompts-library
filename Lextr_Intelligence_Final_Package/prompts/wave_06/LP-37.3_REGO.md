## Comment standard (how this codebase is read six months from now)
- Every new module opens with a header saying what it is for and what it deliberately does not do. Universal in this estate already; now required.
- Comment the DECISION and the rejected alternative, not the mechanism. Why this shape rather than the other one; what was tried and did not survive; what a future reader would otherwise 'fix' and must not.
- A self-correction is recorded WHERE IT WAS WRONG, never tidied away. A wrong edit left beside its correction teaches; a silent fix teaches nothing and invites the same mistake.
- No comment-to-code ratio is set. The measurement is not stable across languages (docstring-heavy Python reads 369% against Java's 38%) and a ratio target is trivially gamed. Enforce the two rules above in review instead.

## Validation gates — how this sub-task is PROVEN, not merely tested
- A gate, not a test count. a survivor is not a pass; a count is not a check.
- Any check whose healthy answer is ZERO needs a positive control. 'No dead seams' is also what a blinded scanner reports. Point the check at something that DOES have the thing, and prove it goes red.
- Execute, don't just resolve. A slice can be BUILT and unreachable; a path can RESOLVE and not bind; a renderer can be IMPORTED and never dispatched; a destination can be REFERENCED and render nothing. A parse gate is not a reference check. THIS CLAUSE NAMES THE SECOND AXIS OF THIS BLOCK, and it is named because it sat unlabelled among clauses about something else for thirty releases. AXIS ONE IS BLINDNESS - can the checker SEE the thing? positive_control, declare_tools, generated_gate, manifest_integrity, prompt_coverage, status_coherence and generated_prompt_review all answer that, and all six known_defect_classes are instances of it. AXIS TWO IS CONNECTEDNESS - is the thing REACHED by production? This clause, config_is_read, reachable_from_root, surface_reachability and wiring_contrast answer that. `rule` and `mutation` bind both axes. The per-language rows (JAVA, PY, TS, REGO, SQL, TEST, CYTO) and wire_through, lane_boilerplate and reason_code_registry are lane and authoring rules sitting under neither; not a third axis. WHY NAME THE AXIS RATHER THAN LEAVE IT IMPLICIT: an unnamed axis is why a reader adds the sixth blindness gate and never the first connectedness gate - the observed history of this block. A CONNECTEDNESS FAILURE IS NOT A COVERAGE FAILURE and no coverage number will ever show one. Every gate on axis two ships the mutant that turns it red, per `mutation`.
- every tool a gate invokes must be a declared dependency - a gate needing an undeclared tool is green for the wrong reason on exactly one machine
- You must mutation-test the gate you write: if no mutant can break a rule, that rule is not being tested. Ship the mutants with the suite.
- EVERY LOOP HALTS AT A CEILING IT DID NOT CHOOSE, AND THE HALT IS RECORDED. `bounded` occurs 102 times in this manifest, `free-roam` 22 times and always negated, and until this gate NOTHING EXECUTED ANY OF IT. A constraint repeated a hundred times and asserted zero times is a paragraph, and validation_gates.rule already says a gate is not a test count - this is the same argument one level up: a gate that nothing runs is a comment. THE RULE: any code path that can call a model more than once - Skill 3 assembly, the graph walk, an agent-framework loop, a retry - reads its ceiling from the resolved PresetSnapshot or governance_envelope (max_steps, and the cost ceiling beside it), never from a constant, a default argument or a literal in the caller. On reaching the ceiling the run STOPS, emits a refusal with its reason code, and persists no partial output as complete - the same posture LP-16 already takes for depth, breadth, node-ceiling and cumulative-token, whose stops are 'all recorded stops (never silent)'. ASSERT, PER PATH: (a) with the fixture ceiling set to N, the path halts at N and the trace carries N steps, not N+1; (b) the ceiling comes from the resolved configuration - changing it in the fixture changes the observed stop, which is what distinguishes a read ceiling from a coincidence; (c) the stop writes a refusal row and the run does not reach a completed status; (d) no path reaches model_abstraction.call without a ceiling in scope - an unbounded caller FAILS THE BUILD rather than defaulting to a generous number. THE POSITIVE CONTROL IS PART OF THE GATE, per validation_gates.positive_control: raise the fixture ceiling and assertion (a) must FAIL; remove the ceiling read and (b) must fail. A ceiling test that passes when the ceiling is deleted is testing nothing, and that is the failure mode this gate exists for - the estate already ships an agent framework whose loop has no asserted bound, recorded in pinned_stack.agent_runtime. SCOPE: this gate binds the lanes whose language gate is PY or JAVA and whose scope reaches a model call; it does not bind a deterministic resolver that calls no model, and LP-09's Skill 1 is named as the example of a path correctly outside it.
- THE KNOWLEDGE HUB IS A RETRIEVAL CORPUS, NOT A SYSTEM OF RECORD, AND UNTIL THIS GATE NOTHING ENFORCED IT. The estate already has the citation half of the rule - LP-25's settled T-4_REVERSED, 'Retrieve from the Hub, CITE from the gold copy' - and it says where a citation is drawn from. It does not say what Hub content may BECOME. Measured at v1.37.1: 'never a source of truth' occurs zero times in this manifest, 'not authoritative' zero, 'grounding only' zero. A boundary nothing asserts is a boundary that holds until the first person in a hurry. THE RULE: NO PRODUCT-DRIVING ARTEFACT MAY TRACE ITS SOURCE TO THE HUB. The product-driving set is closed and named here, because a rule about 'configuration' that does not enumerate it is unrunnable: (a) report setup - report_definition, line, schedule; (b) edit-check expressions and their operands; (c) dependency edges - element_dependency, walk_component, calc-chain; (d) preset and governance_envelope bindings; (e) governed value codes, COA and MDRM identifiers; (f) any DSL or logical attribute name. Every one of those traces to regstruct.* in Lextr Core under GOLD-COPY-SOURCE-OF-TRUTH, arrives through the host adapter read-only, and changes through SDLC. A Hub passage may grounded an ANSWER and may be cited beside one; it may not become one of (a) to (f). ASSERT: (1) no write to a table in the product-driving set carries a provenance whose origin is document_chunk, embedding_store or knowledge_artifact - the origin is a recorded field, so this is a query and not a code review; (2) a skill whose tool_scope permits a Hub retrieval operation does NOT also permit a write to that set - the two op families are disjoint by construction and the Rego is asserted disjoint, not inspected; (3) a run that assembles an answer from Hub retrieval emits output_type NARRATIVE or equivalent and NEVER a definition, an expression or an edge; (4) where a surface offers both - UC11 rules drafting is the live example - the drafted artefact carries an acceptance receipt and enters through the authoring path, never written directly from the retrieval result. THE POSITIVE CONTROL IS PART OF THE GATE, per validation_gates.positive_control: add a fixture that writes an edit-check expression whose provenance names a document_chunk, and assertion (1) must FAIL; widen a Hub skill's tool_scope to include one product-driving write op, and (2) must fail. A boundary test that passes when the boundary is removed is testing nothing - and this is the boundary the whole generative/SDLC split rests on, so it is the one least worth taking on trust. SCOPE NOTE: this gate does not restrict what the Hub may INGEST. Regulatory instruction loaded into the Hub for Q&A is just another document - intelligence.knowledge_artifact treats it as one - and that is the point: the copy in the Hub is for retrieval, the copy in Core is the authority, and only the second one drives anything.
- A wire-through gate is required only where a point actually crosses a boundary its own lanes cannot cover - a wire contract with a host pin, the lexie-ai producer to the Java persist, or ingest through pgvector and out to a policy seam. A single-lane point has no layers to cross and gets no wire-through sub-task. Where one is required it must name the boundary and assert an invariant that neither side can assert alone; '>=90% combined coverage' and 'contract honored end-to-end' are governance_constraints[7] and definition_of_done and are not a test.
- A sub-task whose scope restates a build_context standard is not a unit of work. The standard applies to every lane of its language by default and is asserted by that language's gate; repeating it per point produces one prompt per copy and one more place to drift. Twenty-six such sub-tasks were merged at v1.25.0 - see meta.v26_merge_register. A sub-task earns its place by naming what is true HERE and nowhere else.
- Where a standard is already a table, the gate is GENERATED from the table rather than written as prose beside it. error_conventions.mapping is the worked example: exception FQN -> status -> is_decision -> rationale generates its own conformance test, so an unmapped exception fails the build instead of falling silently to the catch-all.
- The shipped manifest must be byte-identical to what its generator produces from the manifest object, and the verifier RE-RUNS the generator rather than trusting a recorded hash - so 'I only changed one point' is a proof and not a claim. Every release re-runs it, and the release that does not is the one where a hand edit survives. The per-release rebaseline (timeline row, package name, counts) is owned by the packaging point of that release, never by a feature point, because a feature point pins the version it was written against and then goes stale in the only direction that still looks fine. Promoted from LP-47.7 at v1.26.0, where it was pinned to stable_v20 and had not been re-run for five minor versions.
- THE CODE SET IS GENERATED, NEVER HAND-MAINTAINED, AND FOR POLICY CODES IT IS GENERATED FROM THE REGO BUNDLE. Every package returns allow plus deny_reason (the pack's '## REGO BUNDLE SPEC' section, nineteen rows, RUN.md:931-957 - NOT AMD-RUN-48, which v1.28.0 cited in error; see meta.v29_corrections), so THE BUNDLE IS THE POLICY-CODE VOCABULARY. A service-side enum of policy codes would be a second copy of a policy living in application code, which is the thing policy externalisation exists to prevent - and the copy would drift silently, because nothing would fail when the bundle changed. Domain reason codes are generated the same way from the enumerated rule tables that own them; LP-48.2's ingestion rule table is the worked example, where 'a rule added to the table without a code fails the build'. THREE BUILD FAILURES: a policy_code emitted by a service that resolves to no rule in the bundle; a code with no rendering in a shipped locale, per LP-40.tests_must_cover[2] where 'a missing one FAILS THE BUILD rather than falling back silently to English'; and a rule or deny path carrying no code. THE VERBATIM GUARANTEE SURVIVES THIS AND IS NOT WEAKENED BY IT. LP-38 already ships deny reasons 'character-locked across Java/Rego/mirror' and LP-38.tests_must_cover names 'the char-exact verbatim deny reason'. A governed rendering that is byte-identical for a given code is therefore machinery the estate has already built and proven. Verbatim stops travelling as prose and starts travelling as a code whose rendering is locked - which is strictly stronger, because a locked rendering can be diffed and a composed sentence cannot.
- EVERY build_context KEY REACHES A PROMPT OR DECLARES WHY IT DOES NOT. The generator renders its standards blocks from bc.prompt_contract.emit rather than from a list written inside workPrompt(), and this gate asserts that the union of prompt_contract.emit[].key and prompt_contract.exempt covers build_context EXACTLY - a key in neither FAILS THE BUILD, and an exempt entry with no reason string fails too. It runs at the sub-key level for the two blocks that name their keys (error_conventions, validation_gates), because that is where the last five releases lost their clauses. WHY THIS GATE EXISTS: changelog_v1_23_0 states the principle - 'a standard that does not survive into the generated text is not enforced' - and v1.24.0 restates it. Between v1.25.0 and v1.29.0 this programme added TWENTY-SEVEN clauses and wired NONE: error_conventions.gate, .reason_ref, .error_detail, .status_follows_the_rule; validation_gates.wire_through, .lane_boilerplate, .generated_gate, .manifest_integrity, .reason_code_registry; and all seventeen of adoption_standard. A principle stated in a changelog is not a gate. This is the gate.
- A POINT WHOSE STORED STATUS DISAGREES WITH ITS LANES FAILS THE GATE. Every status must be one of build_context.status_model.point_states, and a point stored `ready` while holding a `blocked` lane is the disagreement blocker B4 named: 'both ready_at_start points have zero startable sub-tasks ... a generator driving off sub-task status emits nothing.' THIS GATE FAILS TODAY, on LP-01, LP-02 and LP-48, and it is meant to: B4 is an open blocker and a gate that passes over an open blocker is decoration.
- GENERATE ONE PROMPT PER LANGUAGE AND READ IT, before a release is called done. Seven prompts, one per lang_tax entry. THE THREE IT WOULD HAVE CAUGHT, all at v1.31.0: a point field of the wrong TYPE, which threw; adjustments in the wrong SHAPE, which rendered as undefined; and a hardcoded '>=90%' in a heading whose list had just had the same bar removed. CALIBRATING THIS GATE TOOK TWO ROUNDS, and that is recorded because validation_gates.positive_control requires a gate to be shown able to FAIL and this one had to be shown able NOT to. ## Database conventions (binding on every language, not only SQL)
- Primary keys are bigint GENERATED ALWAYS AS IDENTITY. The Python side must read back DB-generated keys (insert ... returning id) rather than minting uuid4 client-side.
- client_id is mandatory and indexed on every scoped row, and is never in a URL or a query string.
- Tenant isolation is enforced in OPA, not RLS. There is no row-level security in this schema and adding it is a design change, not an implementation detail.
- Migration naming: the dated form V20260604_01__ is the current convention. The three sequential V1__/V2__/V9__ files are the original baseline and are not a precedent.
- New tables and columns are authored Part-M-clean from the start. The existing schema pre-dates Part-M and is embedded verbatim under the downstream-only rule; any Part-M delta on it is an owner-approval proposal, never silently applied.
- policy is never stored in the database. governance_envelope.opa_policy_bindings holds OPA package REFERENCES only; the Rego lives in the policy service.
- embedding_store.embedding is vector(384) and CHECK-pinned to 384, so a wider model cannot silently truncate. A non-384 tenant gets a sibling table.
- The DAO layering - Controller -> Service interface -> DAO interface -> Impl, NamedParameterJdbcTemplate against externalized SQL, no JPA, no inline SQL - is a standing obligation on every Java lane, asserted by validation_gates.JAVA. No point authors its own DAO sub-task; the four acceptance lines (rows affected, rollback on failure, no JPA, SQL loaded from queries.properties) are part of the language gate. Absorbed from LP-03.4 / LP-06.3 / LP-08.4 at v1.25.0.
- THE TENANT GATE, BECAUSE [1] HAS BEEN PROSE SINCE v1.0 AND NOTHING EXECUTES IT. A schema lint runs against the Flyway DDL at build. THREE ASSERTIONS. FIRST, every table outside a DECLARED reference/lookup allow-list carries `client_id NOT NULL`, indexed leading. The allow-list is DATA and EMPTY today - all twelve ddl_body tables carry client_id - so every entry is argued, not default. SECOND, THE HALF NO CLAUSE STATES: `client_id` appears INSIDE every unique constraint and composite foreign key, not merely as a column. IT FAILS TODAY in ddl_body - `embedding_store_chunk_model_uq (chunk_id, model_id)` and `agent_run_step_uq (run_id, step_number)` both omit it, and EVERY FK targets a bare `(id)`, so a child row can point at another tenant's parent and no constraint objects. A uniqueness rule without client_id is one tenant enforcing on another; a single-column FK is a cross-tenant edge the database will happily create. THIRD, no route signature, path segment or query string accepts a tenant - the executable half of [1]. GENERATED per validation_gates.generated_gate from the DDL and the allow-list, so a new table is covered the day it lands. Ships its mutant - drop client_id from one unique constraint, the lint goes red. IT IS EXPECTED TO FAIL ON FIRST RUN, and that is the point: a gate passing over a known defect is decoration - validation_gates.status_coherence's own argument.
- TENANT IDENTITY IS NEVER CALLER-ASSERTED AND NEVER DEFAULTED. It is derived server-side from the verified security principal - the Keycloak token claim - and nothing else. NO REQUEST MODEL CARRIES A TENANT FIELD, and none carries one WITH A DEFAULT, the shape that leaks: the source estate defaults `client_id` to 1 in RuleDescriptionRequest and RuleSummaryRequest and that value flows straight into `WHERE rd.client_id = $1`, returning one client's rows to another on a 200 WITH NO ERROR ANYWHERE. A HEADER IS AN ASSERTION, NOT AN IDENTITY: routes/variance_config_routers.py:58-64 reads X-User-Id and rejects only when absent or empty, so any client sending any value passes - a defect this manifest has WRITTEN DOWN TWICE, at LP-32.pending_items[1] and meta.v29_security_finding, and forbidden in no rule until this one. Sibling routers are weaker still, defaulting the actor to 'anonymous' and 'demo-console'. FAIL CLOSED, WITH NO SECOND READING: A MISSING, MALFORMED OR UNRESOLVABLE TENANT IS A REFUSAL. Never a fallback to a real tenant, never a placeholder resolving to one, never a widened query. Not 'anonymous', not 'demo-console', not 'GLOBAL', not 1, not the first row. The refusal carries a code and typed params per error_conventions.reason_ref and never echoes the asserted value back. WHY NOT DEFAULT-AND-LOG, the tempting middle: the log line is read after the rows are returned.
- A BUSINESS DIMENSION IS NOT A TENANT BOUNDARY. legal_entity, book, desk, cost centre, reporting unit and form family are ATTRIBUTES OF A ROW inside one tenant; `client_id` is the isolation boundary. The two are never collapsed, not even where a deployment happens to run one entity per tenant today - that is a fact about a customer, not a property of the schema. THE DEMONSTRATED CASE IS `legal_entity`: the source estate has no client_id anywhere and used legal_entity as the nearest thing, and legal_entity was itself the subject of the mislabelling defect where TWO VARIANCE CYCLES FOR DIFFERENT ENTITIES RETURNED IDENTICAL REGULATORY FIGURES - a wrong answer nobody detects from a single run, because each run is individually plausible. RECORDED HERE BECAUSE IT IS RECORDED NOWHERE ELSE: `legal_entity` has ZERO occurrences in this manifest, so the case that justifies the rule would otherwise travel as an anecdote and be re-litigated. WHY THE COLLAPSE IS TEMPTING AND STILL WRONG: a business dimension is what the domain talks about and what appears in every filter, so scoping to it FEELS like scoping correctly while the real boundary quietly becomes whatever column the query filtered on. A dimension may narrow a query INSIDE a tenant; it may never separate two tenants, and it is never the column an isolation test asserts on.
- PRIMARY KEYS ARE `bigint GENERATED ALWAYS AS IDENTITY`, READ BACK ON INSERT - [0], restated only to carry its ONE EXCEPTION, ARGUED NOT ASSUMED. An identifier that is PART OF THE DOMAIN CONTRACT may be producer-minted, in three shapes. CONTENT-ADDRESSED: the id IS the digest; a sequence destroys the property the id exists for. CITED IN AN AUDIT CHAIN: LP-26's hash-chained evidence binds a link to an id that must exist BEFORE the row is written; a chain that renumbers on persist is not tamper-evident. EXCHANGED BEFORE THE ROW EXISTS: correlation_id is ECHOED, NEVER MINTED, three-state per error_conventions.error_detail - a sequence cannot represent ABSENT. WHY CARVE RATHER THAN LEAVE IT TO JUDGEMENT: [0] forbids client-minted keys ABSOLUTELY while the estate's own committed work traffics in them, so the convention is broken quietly on the row the audit trail binds to. AN UNARGUED EXCEPTION IS HOW A CONVENTION DIES: the next reader finds a live violation, infers the rule is advisory, and mints uuid4 for a row with none. THE CARVE HAS A SHAPE AND A REGISTER: TEXT, a type prefix, AT LEAST 96 BITS of entropy, listed as DATA beside its contract. The source estate's `analysis_id = va_ + 16 hex` is 64 bits and FAILS that bar: the right exception at the wrong width, which is why the width is stated. Everything else takes the identity column, and the surrogate stays the FK target.
- THE PINNED PHYSICAL CONSTANT IS GATED BY AGREEMENT, NEVER BY ITS VALUE. 384 is not held once and cannot be: it appears in FOUR ARTEFACTS BY CONSTRUCTION and this clause names them, because a rule about 'the number' that does not enumerate its readings is unrunnable. (1) THE MIGRATION COLUMN - ddl_body's `embedding vector(384)` with `embedding_dim integer NOT NULL DEFAULT 384` and `CONSTRAINT embedding_store_dim_chk CHECK (embedding_dim = 384)`. (2) THE SETTINGS DEFAULT AND ITS BOUND - the deployment's embedding-model key, locked by DEC-LP-33-2. (3) THE CALL SITE THAT REQUESTS THE VECTOR - lexie-ai's embedding producer behind LP-04.1's `embedding_call` gate. (4) THE INDEX THAT DEPENDS ON IT - `embedding_store_hnsw_idx ... USING hnsw (embedding vector_cosine_ops)`. THE MANIFEST'S OWN TWO PROSE READINGS ARE INSIDE THE ENUMERATED SET, not outside it - pinned_stack.models ('embeddings all-MiniLM-L6-v2 384-dim') and db_conventions[6] - because a reader believes a sentence here exactly as they believe a column, and a sentence is where a stale width survives longest. THE GATE READS EVERY READING AND ASSERTS THEY ARE EQUAL TO EACH OTHER. IT DOES NOT ASSERT 384. That distinction is known_defect_classes[5] applied to its own subject: a gate that pins the constant tests the constant and not the property the constant stands for, and every mutant that FIXES a stale width is reported as killed - which makes a correct change harder than no gate at all. TWO MUTANTS, AND THE SECOND IS THE ONE A CONSTANT-PINNING GATE CANNOT PRODUCE: change the settings bound alone and the check goes RED; change all six readings together and it stays GREEN. The engine limit is a BOUND ON THE AGREED VALUE, asserted separately, with its own mutant (declare 2049 -> red). IT IS WRITTEN DOWN HERE BECAUSE IT IS WRITTEN DOWN NOWHERE: '2000' has ZERO occurrences in this manifest while `hnsw` has ten, so the index is specified and the ceiling that constrains it is not, and the first proposal for a 4096-dim model meets no objection until CREATE INDEX fails. THE ROUTE TO A DIFFERENT VALUE IS STATED WHERE THE CONSTANT IS, and in this estate it already is: the baseline comment reads 'Divergent-dim tenants get a sibling table embedding_store_<dim> (later migration)'. No Part-M delta is proposed on the embedded DDL - ddl_ownership makes that an owner proposal - and a NEW migration carries its own comment. THE CHECK CONSTRAINT STAYS: the source estate omits it, and it is the only half that survives a writer outside the service.
- APPLIED MIGRATION HISTORY IS NEVER EDITED, AND THE RUNNER HALTS RATHER THAN WARNS. A migration that any environment has applied is immutable. A needed change is a NEW file; where an edit has already happened the reconciliation file states IN ITS OWN HEADER that it is one-time and not a template. The deployment tool keeps a ledger of (filename, content_hash, applied_at, applied_by) WRITTEN AT APPLY TIME and STOPS the deployment when an already-applied file's content differs from its recorded hash. Halt - not warn, not skip, not re-apply. WHAT THE VIOLATION LOOKS LIKE, because it looks like nothing: two environments both report 'migrated' and are running different schemas, and no artefact records which is which. The divergence is a function of WHEN each database last migrated, which nothing writes down, and it surfaces on the NEXT migration rather than the edited one - so the symptom is a plausible figure from one environment and a different plausible figure from its sibling, with no error in either. THIS IS NOT db_conventions[4] AND NOT validation_gates.manifest_integrity, and the difference is the point of stating it. [4] governs AUTHORSHIP: a Part-M delta on the embedded baseline is an owner-approval proposal, never silently applied. It decides who may change a schema and by what route and says nothing about a file that has already run - so it binds an APPROVED edit not at all, while this clause binds an approved edit exactly as hard as an unapproved one. Owner approval is a licence to write a NEW migration, never to edit an applied one. manifest_integrity refuses a recorded hash ON PRINCIPLE and RE-RUNS the generator, because the manifest is DERIVABLE and 'I only changed one point' must be a proof rather than a claim. A migration is not derivable: its effect lives in a database and there is no generator to re-run, so a recorded hash is the only evidence available. WHAT MAKES IT ACCEPTABLE HERE IS WHO WRITES IT - the runner writes the row as a side effect of applying, under its own credentials, so nobody maintains it and nobody can bring it into line by hand. LP-26 records the opposite case as a known limit ('a checksum manifest would go stale silently'); that manifest was hand-maintained, and staleness is precisely the condition this ledger REPORTS. THE LEDGER IS NOT NEW MACHINERY AND MUST NOT BE BUILT TWICE: the DDL is Flyway-owned, `flyway_schema_history` already carries a checksum per applied migration, and what this clause adds is the DISCIPLINE around it - `validate` runs against an ALREADY-MIGRATED environment, not only the clean one, and `repair` is prohibited on a changed migration because repair rewrites the recorded checksum to match the edited file and converts the halt into a silent pass. LP-01.manifest_of_steps already runs `flyway validate`, on a CLEAN PG16 - the single run in which a changed applied file cannot be detected - and migrate_check.sh checks 'from empty' for the same reason. THE RUNNER ALSO REDACTS CREDENTIALS BEFORE PRINTING A DSN and probes for the required extension before starting, so a missing pgvector fails with an actionable message instead of half-applying. MUTANT: change one byte of a comment in an applied migration - the deploy halts and names the file, while every unit suite stays green.

The tenant lint is renamed with it and keeps its full force: client_id NOT NULL and indexed outside the allow-list, INSIDE every unique constraint and composite foreign key, never in a route signature, path segment or query string. A lint naming a column that no longer exists passes by finding nothing. AND THE NAME IS ADOPTED, NOT THE BEHAVIOUR: every earlier reference to client_id in this manifest is a RECORDED DEFECT of the source estate - a caller-asserted default of 1 reaching a live WHERE clause. ## Definition of done
- the sub-task's own tests pass AND its gate is shown able to fail
- the README ships with it - see the governance bar for its required sections
- every claim in the README is one you ran, not one you expect; anything not run is named as not run
- open items are recorded as open items, with an owner
- the deliverable's CONFIGURATION IS READ - every key it declares is consumed by a module that is neither the settings object nor the catalogue, asserted by validation_gates.config_is_read. A knob shipped with bounds, an audit row and no reader hands the operator a complete receipt for a change that did nothing, and no coverage number will ever show it. A deliverable that declares no configuration says so: 'none' is an answer and an empty field is not.
- the deliverable is REACHABLE FROM THE COMPOSITION ROOT and a test EXECUTES it from there, per validation_gates.reachable_from_root. Reachable alone is not enough and executed-in-isolation is not enough either - a unit test that instantiates the class proves the class works and proves nothing about whether the running application ever constructs it. The PATH from root to entry point is the assertion, and a reference that exists only under tests/ does not count toward it.
- the DEGRADATIONS it can enter are ENUMERATED on the health surface, and EACH ONE NAMES ITS FIX. Self-healing is governance_constraints[8]; this is the half that makes it operable. A capability running degraded because a key is unset, a circuit is open or a dependency is unreachable must say which of those it is and what to set - a degradation an operator cannot see is indistinguishable from working, and one they can see but cannot name sends them to the wrong system. The bare word 'degraded' is not an enumeration, and a health surface that only ever reports UP has not been shown able to fail.

## Adoption standard
- An entry in a point's manifest_of_steps or tests_must_cover is a REQUIREMENT, not a sub-task, and adoption is not complete until the sub-task that carries it exists. No sub-task in this manifest carries manifest_of_steps. An item that lands on a point and authors no sub-task produces LP-04's defect - six steps and seven tests against one sub-task - and LP-36's, where five steps face one generic wire-through lane that implements none of them.
- A sub-task's scope names what is true HERE and nowhere else. A scope that restates a build_context standard, or repeats one of the eight boilerplate scaffolds, is rejected: thirty of forty-seven points have no point-specific sub-task content, and the harvest must reduce that number, never raise it.
- Every adopted item declares POLICY, GATE or NEITHER. POLICY names a package AND a rule and describes the runtime decision - who is asking, what op, which datum. GATE names the build check and the mutant that turns it red. NEITHER names what does enforce the item, whether a database constraint, a composition-root rule or a contract. A build gate and a runtime policy are different controls; an item claiming Rego coverage for a rule a policy engine has no input to decide is the claim this estate exists to catch.
- An item declaring POLICY against a package it does not author cites the owning point and the rule it reuses. LP-04 owns the bundle root and the shared packages; a use case authors its own tool_scope_<uc> against that contract; a point with no package of its own gets NO Rego lane and instead declares the datums it supplies and the package that gates it. An item that would author a second package deciding a question an existing package already decides is rejected under anti_dup.hard_rules.
- Every adopted item answers what becomes DATA - a policy, a governed table, a registry row, a catalogue - and what deliberately stays code, with the reason. Configuration means a governed catalogue: each key carries type, bounds, a consequence class and one sentence of blast radius; refusals name their reason as data; rows are superseded, never updated. An item that becomes nothing declares null rather than leaving the field empty.
- A key published without a code path that reads it is worse than no key, because the operator gets a complete receipt for a change that did nothing. No item may specify a catalogue, a setting or a governed row without validation_gates.config_is_read over it.
- Adoption honours reuse > configuration > extension > new and states which of the four it is, with file paths. An item that creates a second owner of an existing object - a second package deciding one question, a second subject key, a second population owner, a second governed write path outside the preset envelope - is rejected regardless of how much better the new one is. Duplication is the failure mode this manifest exists to prevent, and a second authority is a divergence waiting for the day the two disagree.
- An item landing on a committed point reopens it: the point declares the divergence in pending_items with an owner, and its status is re-derived rather than left standing. A committed point that gains scope and keeps its status is a claim nobody produced.
- AN ITEM'S CITATION NAMES THE FILE THAT CONTAINS THE BEHAVIOUR IT CLAIMS. source_path is not where the reading started and not where the reader happened to be; it is the file a second person opens to see the thing the item says is there. An item whose claims span several files cites EACH ONE and says what that file supports - the mechanism in one, the quoted text in another, the default in a third - because a single path against a multi-file claim tells the next reader that everything is in one place and it is not. AND EVERY FIGURE IN A CLAIM IS CHECKABLE, SO IT MUST HAVE BEEN CHECKED: a count, a file size, a port, a line range, a ratio, a version - each is a number the source already holds, and an item may not hold its own copy of it. A figure nobody counted is not evidence, it is a recollection. This clause binds the harvest record itself and not only what the harvest lands; it applies retrospectively to every item already adopted, which is the reason it is written as an obligation rather than as a note.
